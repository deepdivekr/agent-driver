# 자율 운영 리팩토링 계획 (초안)

Status: **초안 — 사용자 검토 대기.** 승인되면 S0에서 AGENTS.md가 가리키는
기준 문서로 지정한다. 그 전까지 [커스텀 Pack 리팩토링 계획](custom-pack-refactoring-plan.md)이
기준이며, 이 문서는 그 계획과 충돌하는 조항을 명시적으로 표시한다.
Baseline: main f077e04 (PR #36 머지 포함).

## 1. 목표

사용자가 원하는 제품은 **직원에게 일을 맡기고 막힐 때마다 도와주는 도구가 아니라,
한 번 위임하면 스스로 끝까지 하는 에이전트 관제센터**다.

1. 새 Work를 등록하면 에이전트가 절차를 설계하고 실행한다.
2. 실행 중에 사용자가 방향을 바꾸면 이미 끝난 부분은 살리고 나머지를 다시 짠다.
3. 성공한 Work는 **자동으로** Pack이 된다. 여러 단계짜리 Work도 포함한다.
4. 새 Work를 계획할 때 에이전트가 **스스로** 맞는 Pack을 골라 재사용한다.
5. 반복될수록 결정적인 부분은 코드(스크립트)로, 짧은 판단은 Jev로 옮겨져
   더 빠르고 안정적이 된다.
6. 막히면 **스스로** 다른 엔진·실행 환경·출처·도구로 넘어간다.
7. `failed`로 끝나지 않는다. 사람이 꼭 필요한 극소수 경우만 알림을 보내고,
   나머지는 보류 후 자동 재시도한다.

### 사람 개입의 원칙

사람은 **처음에 위임 정책을 한 번 정한다.** 이후에는 정책 안에서 에이전트가
결정하고, 사람은 결과 알림만 받는다. 건별 승인은 없앤다.

정책으로도 대신할 수 없는 사람 개입은 다음 세 가지뿐이다.

| 경우 | 이유 | 빈도 |
|---|---|---|
| 사이트 최초 로그인·2단계 인증 | 신원 확인은 본인만 가능 | 사이트당 1회, 이후 전용 프로필에 유지 |
| 필수 서비스의 CAPTCHA | 우회는 이용약관 위반·계정 차단 위험 | 대체 출처를 먼저 자동 시도 후에만 |
| 정책 밖의 되돌릴 수 없는 외부 행동 | 결제·제3자 발송·제출 | 정책에서 유형별로 허용하면 0회 |

## 3. 운영 원칙 (3층)

AGENTS.md와 기존 계획서를 아래 구조로 다시 쓴다(S0).

### 3.1 절대 유지
- 성공을 허위로 보고하지 않는다. **거짓 거부도 결함으로 측정한다.**
- 인증정보·개인 데이터를 노출하지 않는다.
- **위임 정책** 밖의 행동을 하지 않는다. 권한은 건별 승인이 아니라 사용자가
  정한 위임 정책이며, 호스트가 집행한다. 모델이 스스로 권한을 만들지 못한다.
- 원래 요구와 이후 지시를 기준으로 삼는다. 기존 receipt는 지우거나 고쳐 쓰지
  않는다(“대체됨” 표시는 삭제가 아니다).

### 3.2 조건부 복구
- 읽기: 언제든 다시 조회한다.
- 로컬 쓰기: Office 소유 산출물은 새 요청 ID로 다시 쓰거나, 같은 대상·같은
  내용이면 멱등 처리한다. 사용자 폴더 쓰기는 대상 상태를 다시 읽어 확인한 뒤 재시도한다.
- 외부 쓰기: 반영 여부를 먼저 조회해 확인한다. 반영됐으면 재사용하고,
  안 됐으면 재시도한다. 확인할 방법이 없을 때만 사람에게 알린다.

### 3.3 자율 운영 (신규)
- 위임 정책 한 번 설정 → 건별 승인 없음.
- 성공 Work 자동 Pack화, 성적 기반 승격·강등.
- 계획 단계 Pack 자동 선택, 실패 시 같은 Work 안에서 새로 계획.
- 막히면 정책이 허용한 다음 수단으로 자동 전환.
- `failed` 대신 `deferred`(자동 재시도) 또는 `needs_user`(1장의 세 경우).
- 1차 지표: 완료율, 거짓 거부율, Work당 사람 개입 횟수, 반복 시 모델 호출·시간 감소.

### 3.4 기존 계획서에서 바뀌는 조항

| 기존 조항 | 변경 |
|---|---|

| R4 “draft와 ready를 구분… 활성 버전을 만들지 않는다” | 자동 후보 → 성적 기반 자동 승격(S4) |

| R4 “회차 준비는 새 Work를 만들고 실행하지 않는다… current_run_only 요구” | 정책 안에서 준비와 실행을 한 번에(S5) |

## 4. 구현 단위

각 단위는 독립적으로 머지할 수 있다. 단위마다 빌드, 관련 테스트, frozen quick
suite를 통과하고, 진행 기록을 갱신한다.

### S0. 기준 전환 (문서)
- AGENTS.md의 Reliability constraints를 3장의 3층 구조로 다시 쓴다.
- 이 문서를 기준 문서로 지정한다. 기존 계획서는 이력으로 남기고, 3.4의 조항에
  “대체됨” 표시를 한다.
- 완료 기준: 사용자 승인, 다른 에이전트(Codex 등)가 같은 문서를 읽음.

### S1. 위임 정책
- 호스트 소유 정책 객체 하나를 버전과 함께 저장한다.
  - 실행 환경: 백그라운드 / 같은 환경의 다른 엔진 / Aside / 전용 VM 화면 /
    사용자 데스크톱(자리 비움일 때만; 기본 꺼짐)
  - 효과 유형: 읽기 / Office 산출물 쓰기 / 등록 폴더 쓰기 / 초안 /
    본인에게 보내는 알림 / 제3자 발송 / 제출 / 결제 (뒤의 셋은 기본 거부)
  - 예산: 구독 모델 일일 호출 한도, Work당 재시도 시간 한도, 유료 API 자동 사용 금지 유지
  - 알림 수준: 성공·`needs_user`만 / 전체
- 건별 게이트를 정책 조회로 바꾼다.
  - 실행마다 모델 사용 동의: `src/work/supervisor.ts:155`, `src/work/dispatch.ts:58`
  - 로컬 Pack 쓰기 제안 승인: `src/work/execution-tools.ts:727`
  - 일정·커스텀 일정 승인: `src/work/custom-pack-schedule.ts:16`
  - Jev 비용 동의: `src/packs/store.ts:446` (정책 예산 안이면 자동)
- 모든 행동 기록에 허용한 정책 버전을 남긴다.
- 기본값 하나로 바로 쓸 수 있게 한다. 첫 실행 화면에서 한 번 확인하고 끝낸다.
- 완료 기준: 정책 안의 Work가 사람 클릭 없이 접수부터 결과까지 진행된다.
  정책 밖 행동은 실행되지 않고 `needs_user`로 남는다.

### S2. 완료 경로 정상화 (S4의 전제)
자동 Pack화는 “성공” 판정이 믿을 만해야 의미가 있다.
- 대체된 산출물: 같은 대상을 나중에 다시 쓴 경우 등 호스트가 아는 사실로
  “대체됨”을 표시한다. 배치 검사의 `contradicts`/`unresolved_material`은 즉시
  거부(`src/work/completion.ts:410`)하지 않고 최종 판단의 입력으로 넘긴다.
  모순 증거는 숨기지 않는다.
- 검사별 근거: 생성된 검사에는 그 검사가 인용한 receipt와 해당 단계의 receipt만
  붙인다. 전체 receipt는 원래 요청 검사에만 붙인다(`src/work/supervisor.ts:40`).
- 표 데이터: 셀 단위 인용 목록을 행 단위로 압축해 실행기 receipt 한도(16KB)와
  검증 한도를 맞춘다(`src/work/completion.ts:317`).
- 실행기: 완료 제안의 검사 누락·잘못된 ID는 출력 교정 1회로 처리하고 `failed`로
  끝내지 않는다(`src/work/client-executor.ts:401`, `:519`).
- 수정 루프: 거부 이유를 수정 입력에 넣는다(`completionRepairFeedbackSchema`).
  수정 기회는 정책 예산 안에서 여러 번(기본 3회). 인용 오류·한도 초과 같은 검증기
  기술 실패는 Work 보류가 아니라 검증 재시도로 처리한다.
- 로컬 쓰기 재시도: 3.2에 따라 허용한다(`src/work/client-executor.ts:490`).
- 실행 trace: receipt 재사용도 관측으로 기록한다(`:457`). 32개 관측 창과 별개로
  trace용 전체 이력을 보존한다(`:282`).
- 완료 기준: 세 시뮬레이션(대체된 초안, 완료 제안 형식 오류, 180행 표)이 통과한다.
  기존 거짓 성공 방지 테스트는 모두 유지한다.

### S3. 상태 모델: 실패 대신 보류
- 최종 상태를 `succeeded`, `deferred`, `needs_user` 세 가지로 정리한다.
  - `deferred`: 백오프로 자동 재시도한다. supervisor tick이 집어 간다
    (`src/work/supervisor.ts:241`).
  - `needs_user`: 1장의 세 경우와 정책 밖 행동만. 사유와 해야 할 일 하나를 알린다.
- 기존 상태 매핑:
  - `retryable_failure` 3회 후 `failed` → 정책 예산 안 `deferred`(`:433`)
  - `waiting_model` → 쿼터 회복 시각에 자동 재개
  - `awaiting_review` → 자동 재계획 루프. 예산 소진 시 `deferred`
  - `reconciliation_required` → 대상 상태를 먼저 자동 조회, 확인 불가일 때만 `needs_user`
  - `waiting_connection`(설정 변경) → 이 Work가 쓰는 설정이 바뀐 경우만.
    설정 결속을 전체 해시에서 의존 대상 해시로 바꾼다(`src/interface/config.ts:145`, `src/work/supervisor.ts:216`, `:258`)
- 기존 상태 값은 호환 독자로 계속 읽는다.
- 완료 기준: 일시적 장애(모델 쿼터, 네트워크, 설정 변경)를 넣은 장기 실행
  시험에서 사람 조작 없이 회복한다.

### S4. 자동 Pack화와 성적 관리
- 검증을 통과한 Work의 절차를 자동 저장한다. 절차의 구성:
  - 계획 단계와 의존 관계
  - 단계별 성공 호출 템플릿: 도구, 인자, 사용자 입력·날짜에서 뽑은 파라미터
  - 단계 종류: 결정적(코드로 재생 가능) / 판단(모델·Jev 필요)
  - 완료 계약, 봉인된 수집 계약, 관측된 출처 스키마
- 여러 recipe·여러 단계 Work를 허용한다(`src/packs/custom-registry.ts:114` 제거).
- 생애 주기:
  - 처음엔 후보, 검증 통과 K회(기본 2회, 원본 포함) 후 자동 정식
  - 환경 원인이 아닌 연속 실패 2회면 자동 강등
  - 버전은 불변 유지, 절차가 바뀌면 새 버전
- 결속: 설정 전체 해시(`:96`, `:144`) 대신 그 Pack이 쓰는 출처·대상·실행기와
  엔진 버전만 묶는다.
- 관제센터에 Pack 목록, 성적, 사용 이력을 보여준다. 끄기만 사람이 할 수 있고 등록 승인은 없다.
- 기존 수동 MCP 등록과 저장된 Pack은 호환 유지한다.
- 완료 기준: 성공 Work → 후보 Pack 자동 생성 → 두 번째 성공 → 정식 승격까지
  사람 조작 0회.

### S5. 계획 단계 Pack 자동 선택
- 계획 입력(`src/work/runtime.ts:41`)에 Pack 후보를 넣는다. 코드가 먼저 업무 분류,
  출처, 출력 형식, 키워드로 상위 N개를 고르고 성적과 함께 전달한다.
- 계획 출력에 `pack_selection: {key, version, parameters, fit_reason} | null`을 추가한다.
- 호스트가 파라미터를 Pack 스키마로 검증하고, 회차 준비와 실행을 한 번에 한다
  (`src/interface/api.ts:302`의 `current_run_only` 요구를 정책으로 대체).
- 맞지 않거나 실패하면 같은 Work 안에서 일반 계획으로 넘어가 계속한다.
  결과는 Pack 성적에 반영한다.
- 새 Work의 원래 요청 검증은 그대로 수행한다. Pack의 과거 성공은 이번 결과의 증거가 아니다.
- 완료 기준: 비슷한 두 번째 Work가 Pack을 재사용하고, 첫 실행 대비 모델 호출이 줄어든다.

### S6. 스크립트화와 Jev
새 워크플로 엔진을 만들지 않고, 기존 실행기 루프에 “이미 정해진 결정”의
공급원을 추가한다.
- 1단계(안내): 실행기에 검증된 절차와 템플릿을 주어 턴 수를 줄인다.
- 2단계(재생): 결정적 단계는 호스트가 모델 턴 없이 템플릿으로 실행한다.
  판단 단계와 이탈(오류, 결과 형태 불일치)만 모델에 넘기고, 그 지점부터는
  일반 루프로 이어 간다.
- 판단 단계 중 선택지가 정해진 짧은 판단은 Jev가 켜져 있고 예산 안이면 Jev로,
  불확실하면 LLM으로 돌아간다.
- 측정: 같은 Pack의 회차별 모델 호출 수, 소요 시간, 성공률.
- 완료 기준: 결정적 단계만 있는 Pack 회차는 검증을 빼고 모델 호출 0회로 실행된다.

### S7. 실행 수단 단계 전환
- 라우터(`src/browser/executor-routing.ts:192`, `:204`)를 정책 기반 사다리로 바꾼다:
  전용 백그라운드 → 같은 환경의 다른 엔진 → Aside(읽기) →
  **전용 VM 화면**(`src/isolation/ubuntu-browser-vm.ts`, 로그인 유지 프로필) →
  사용자 데스크톱(정책 허용·자리 비움일 때만) → 다른 출처·도구로 재계획.
- 전용 VM은 사용자 화면이 아니므로 “포그라운드 승인” 단계가 필요 없다.
  최초 로그인만 VNC로 한 번 `needs_user`.
- 쓰기는 쓰기를 지원하는 환경에서만 한다(현재 Neo·Aside는 읽기 전용).
  효과가 불확실한 중간에는 전환하지 않는다.
- 대체 수단 탐색은 등록된 실행기·출처·설치된 CLI/API 안에서 한다.
  범용 도구 마켓플레이스는 계속 범위 밖이다.
- 봉인된 수집 계약(`src/work/execution-tools.ts:438`): 사용자가 출처를 지정하지
  않았다면 출처가 막혔을 때 에이전트가 새 계약을 다시 봉인할 수 있다.
  원래 요청 검증이 바뀐 출처를 그대로 확인한다.
- 완료 기준: 백그라운드 차단·로그인 만료·출처 장애를 넣은 시험에서 사람 개입 없이
  다음 수단으로 넘어가 완료한다(최초 로그인 제외).

### S8. 실행 중 방향 전환
- Swarm: 단계가 바뀌면 정지하는 대신(`src/work/swarm-executor.ts:200-202`)
  결속이 같은 작업자는 유지하고, 바뀐 단계만 다시 계획해 이어 간다.
- 실행 방식 변경(`src/work/supervisor.ts:386`): 기존 receipt를 상속 증거로 넘겨 이어 간다.
- 완료 기준: 실행 중 지시 변경이 정지 없이 반영되고, 끝난 단계는 다시 실행하지 않는다.

### S9. 흩어진 봇 통합 (다음 차례)
가져온 Hermes·원격 OpenClaw 등은 지금 “원본에 메시지 보내기” 수준으로 제어된다.
S1–S8 이후, 가져온 봇의 단계 관측과 방향 전환을 같은 Work 모델로 끌어온다.
이번 1·2차 범위에는 넣지 않는다.

### S10. 실제 모델 기준 측정 (전 기간)
- fixture 테스트는 계속 쓰되 “fixture”로 표시한다. 수용 판정은 실제 구독 모델로 한다.
- 측정 세트:
  - 공개 재현 세트 6–8건(조사, 수집, 파일 변환, 감시, 폼 초안). 누구나 다시 돌릴 수 있다.
  - 비공개 원본 24건. 사용자 환경에서만 돌리고 공개 기록에는 수치만 남긴다.
- 지표:
  - 완료율
  - 거짓 거부율: 거부된 건을 표본으로 사람이 확인
  - 거짓 성공률: 성공 건 표본 확인
  - Work당 사람 개입 횟수
  - Work당 모델 호출 수와 소요 시간, 반복 회차 감소율
  - Pack 재사용 적중률
- 초기 목표(사용자 확인 필요):
  - 공개 세트 완료율 70% 이상
  - 사람 개입은 새 사이트 로그인 외 0회
  - 정식 Pack 회차의 모델 호출이 첫 실행 대비 50% 이하
