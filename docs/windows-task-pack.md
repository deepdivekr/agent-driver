# Windows Task Pack

Windows 업무도 한 줄 Work에서 시작한다. LLM이 연결된 실행기와 실제 컨트롤을 보고
절차를 만들고, 기존 Pack의 판단 정책과 실행 기록으로 수행한다. 아래 10개 프로필은
예시·최적화 자료이지 지원 앱 목록이나 필수 등록 단계가 아니다. 새로운 앱마다
프로필 코드를 추가해야 한다는 의미도 아니다. 새 Pack family를 추가하지 않았다.

## 현재 제공 범위

Phase 80의 공통 CUA 연결기는 Work에서 생성한 절차를 실행한다. 관측된 UIA 컨트롤의
클릭·입력과 긍정적인 재확인 조건을 사용한다. 초기 연결·창 접근 권한은 필요하지만
필드 번호나 앱별 실행 스크립트를 작성할 필요는 없다. 전용 연결 없이 기본 설치만
한 상태를 준비 완료로 표시하지 않는다.

실제 Windows 문자표에서 구독 Codex가 Work와 절차를 생성하고, 공통 CUA 경로로
입력·재확인·절차 재사용을 통과했다. Phase 81은 UIA가 부족하면 현재 창의 로컬 OCR
후보로 화면 이동을 보완한다. 자동 창 권한 획득 UI, 외부 전송 승인 UI까지 모두
연결됐다는 뜻은 아니다.

UIA가 충분한 단계는 스크린샷 없이 진행한다. UIA가 없는 단계는 현재 창을 캡처해
글자 위치 후보를 만들며, 혼합 화면은 `runtime_windows_design`의 `observation: visual`로
보완 관측할 수 있다. 이것은 DOM 생성이 아니며, OCR 후보의 활성 여부·확률은 `unknown`
의미의 `null`이다. Jev/LLM은 후보를 선택하고 코드는 현재 캡처 좌표·권한·결과를 검증한다.
반복 실행도 현재 화면은 확인하되, 동일 화면은 OCR을 재사용하고 바뀐 영역만 다시 읽는다.
별도 앱 프로필은 필요 없다. 현재 시각 경로의 검증 가능한 동작은 글자가 있는 대상의
화면 이동이다. 글자 없는 아이콘·시각 전용 편집칸·전송까지 지원한다고 표시하지 않는다.

앱 버전별 메뉴 차이, 복합 필터, 커스텀 컨트롤은 추가 관측과 LLM 재계획이 필요하다.
현재 관측이 절차와 달라지면 재관측·LLM 재계획으로 넘긴다. 모든 앱이 동일한 UIA
트리를 제공한다고 가정하지 않는다. 카카오톡을 본인 대화로 한정하는 전역 제한은
없다. 사용자가 지정한 상대·대화방이 대상이다. 위 본인 대화 프로필의 경계는
실제로 본인 대화를 요청한 경우에만 적용한다. 새 전송 증거와 승인은 별개다.

## 연결과 호출

1. 기존 `runtime_work_start`로 Work를 만든다. LLM은 같은 Pack family를 선택한다.
2. `runtime_windows_catalog`로 실제 연결 상태를 확인한다.
3. `runtime_windows_design`에 Work ID를 전달한다. LLM이 현재 연결·관측에 맞게
   절차를 만들거나 검증된 절차를 재사용한다. `runtime_windows_plan`은 선택적인 예시 조회다.
4. `runtime_windows_start`에 Work ID와 정확한 입력을 전달한다. 시작 자체는 클릭하지 않는다.
5. 연결된 경우 `runtime_windows_step`을 현재 revision으로 호출한다. 한 호출당 최대 한 동작이다.
6. `runtime_windows_status`와 `runtime_work_status.windows_runs`에서 단계·증거·중단 원인을 확인한다.
7. 응답 유실 등으로 효과가 불확실하면 `runtime_windows_reconcile`로 같은 실행기에
   결과 재조회를 요청한다. 이 호출은 클릭·입력·전송을 하지 않는다.

기존 `runtime_pack_plan`도 이 Work 기반 경로와 선택적 예시를 알려준다. 대시보드에
별도 바탕화면 정리 페이지를 만들지 않았다. 단계 완료는 Work 전체 완료와 분리한다.
파일 정리 프로필은 `runtime_files_scan/classify/propose`로 이어져야 정리안이 완성된다.

`WindowsWorkflowDriver`는 런타임을 구성하는 신뢰된 host 코드에만 주입한다.
MCP 인자로 driver, 허위 관측, 승인 여부를 넣을 수 없다. 기존 `@oai/sky`는 이 개발
세션의 Computer Use 도구이며 제품에 배포되는 Windows 연결기와 동일하지 않다.
이를 썼더라도 별도 연동 증거 없이 Agent Driver 네이티브 성공이라고 표시하지 않는다.

## Jev의 역할과 제한

- UIA/검증된 OCR 등 host 관측을 텍스트 후보 표로 만든다. 현재 Jev는 이미지 입력 모델이 아니다.
- 같은 관측에서 `windows.stage_state`와 `windows.target`을 한 요청으로 묻는다.
- Jev는 대상 선택을 제안한다. 클릭 좌표·입력 본문·스크립트를 생성하지 않는다.
- 메시지 본문·파일 내용·원시 UI 트리·스크린샷·자격증명은 이 판단 요청에 넣지 않는다.
- 파일명·열 이름·슬라이드·필드처럼 대상을 특정하는 값은 프로필의 허용 목록에서만
  가져온다. 각 값은 512자 이내이며, 대상 정보가 빠지면 추측하여 실행하지 않는다.
- 생성된 절차에서 이미 정확히 지정했고 현재 유일하게 관측된 초안 입력칸은
  추가 모델 판단 없이 코드가 선택한다. 이것을 반복 성공 캐시 적중으로 세지 않는다.
- 이미 검증된 단계는 코드가 건너뛴다. 불확실한 선택만 연결된 LLM이 보정한다.
- LLM 보정도 화면이 해당 단계에 준비됐다는 판단과 실제 후보 라벨 인용을 함께
  반환해야 한다. 모델 응답은 승인이나 작업 완료 증거가 되지 않는다.
- 전역 Jev OFF, Work의 명시적 OFF, Pack의 모델 OFF 및 데이터 전송 동의를 따른다.
  Work 설계 때 별도의 Jev 정책을 다시 만들지 않는다.
- 확신도와 선택 확률을 별도로 기록한다. 초기 .9 기준은 제품 기본값이며 한국어 Windows
  앱에서 calibration이 완료되었다는 뜻이 아니다. 실환경 labeled holdout으로 검증해야 한다.
- 공통 Decision Plane의 profile registry와 `decisions/windows.jsonl`을 사용한다.
  `runtime_decision_status`에서 다른 판단군과 함께 확인한다.
- 단계 receipt의 토큰 수는 `usage_scope: jev_primary_only`이다. LLM 보정·shadow
  사용량까지 합친 총 비용으로 해석하면 안 된다. 미관측 사용량은 `unobserved`다.

## 네이티브 연결기가 지켜야 할 계약

관측은 실제 앱과 창에 묶고, 비밀번호·인증·보안·잠금 화면을 분리한다. 입력 전후 증거는
해당 run의 입력·Work revision에 묶인 해시를 포함한다. 외부 전송 완료는 이번 action ID에
연결된 새 메시지 증거가 필요하다. 이전에 같은 문장이 있다는 이유로 성공 처리하지 않는다.

모든 동작에 host 범위 승인을 검사한다. 전송·새 파일 저장에는 해당 payload와 대상의
단일 사용 인간 승인이 필요하다. 자동 동기화되는 초안, 자동 전송 필드, 자동 저장 원본도
실제 외부/원본 효과로 취급해야 한다. 어댑터가 이를 보장할 수 없으면 거절한다.

런타임은 모델 응답 후와 승인 후 다시 관측한다. 어댑터도 입력하는 순간 창·포커스·대상·
관측 해시를 원자적으로 검사해야 한다. 런타임의 관측만으로 TOCTOU가 사라지지 않는다.
foreground 소유권은 전체 host에서 직렬화해야 한다. 현재 SQLite 잠금은 같은 DB의
같은 driver ID만 직렬화한다. 다른 DB/외부 앱을 포함하는 host 잠금은 어댑터 책임이다.

동작 직전 `executing`을 저장한다. 프로세스 중단·응답 유실·검증 실패는
`reconciliation_required`로 남기며 재전송하지 않는다. 불확실 효과 잠금은 보존한다.
`runtime_windows_reconcile`은 저장된 정확한 명령과 action ID를 같은 host에 넘긴다.
host가 뒤늦은 입력까지 차단한 상태임을 확인하고, 실행했으면 동작에 연결된 새 증거를,
실행하지 않았으면 실행기 자체의 미실행 증거를 돌려줘야 한다. 화면에서 메시지가
안 보인다는 사실만으로 미전송 판정을 해서는 안 된다. 검증된 결과 저장과 잠금 해제는
한 SQLite 트랜잭션이다. Work 일시정지 중에도 결과 확인은 가능하지만 다음 동작은
여전히 일시정지·지침 revision 검사를 통과해야 한다.

MCP 호출자가 성공·미실행·승인을 입력할 수는 없다. 증거가 없거나 옛 명령이 저장되지
않은 실행은 잠금을 유지한다. 현재 사용자용 네이티브 연결/복구 화면은 없으며,
배포용 어댑터가 실제 Windows 관측·입력·뒤늦은 동작 차단·독립 재조회까지 구현해야 한다.

## 이번 검증의 해석

2026-09-28 Phase 77: 기본 Windows 연결 경로로 런타임이 직접 소유하는
`CuaFieldDriver`를 추가했다. Windows 호스트 설정의 `windows_executor`에서
CUA 자식 프로세스를 시작하며 Codex Computer Use가 필요하지 않다.
실제 MCP → Work → CUA → 로컬 입력 → 독립 재확인까지 통과했다.
최종 표본의 실행 단계는 9.004초, 새 LLM/Jev 호출은 0회다.
현재 지원은 검토된 단일 로컬 입력칸으로 한정되며, 카카오톡 등 다른
프로필의 실동작 성공을 의미하지 않는다. 자세한 설정·실패·측정 범위는
`docs/owned-windows-executor.md`를 참조한다. 아래 Phase 76 기록은 과거 결과다.

2026-09-28 Phase 76: `Window2FieldDriver`를 추가했다. 연결된 호스트가 공개
window2 클라이언트를 주입하면, 검토한 창 하나의 로컬 단일 입력칸에 한해
`windows.form.draft`를 실행할 수 있는 연결부다. 범용 클릭, 카카오톡, 인증,
터미널, 자동 제출을 지원한다고 표시하지 않는다. MCP 호출자는 창 바인딩이나
승인을 만들어낼 수 없다. 원본 UI 트리·필드 내용은 판단 모델에 넘기지 않고,
라벨·필드 의도와 해시만 관측 계약에 넣는다.

실제 Windows 호스트에서 실행기 연결과 Codex 구독을 통한 Work 생성까지 확인했다.
입력 전 재관측에서 사용자가 Escape로 Computer Use를 중단해 실제 입력·재확인은
미실행이다. 아래 fixture 결과를 이 실동작 성공으로 대체해서는 안 된다.
현재 Codex 클라이언트가 제공한 실행 포트를 사용한 것이며, 누구나 설치하면
자동 연결되는 독립 Windows 서비스가 포함됐다는 뜻은 아니다.
회귀 검사와 남은 범위는 `docs/handoff/phase-76.md`에 기록했다.

테스트의 driver·Jev·LLM 응답은 명시적인 fixture다. 실제 SQLite 저장·재시작 경계는
검사하지만, 카카오톡·Outlook·Office에서 성공했다는 증거가 아니다. 실제 사용자 PC에서
한 번도 검증하지 않은 프로필은 `native_app_coverage: unverified`를 유지한다.

Windows에서 Decision profile 저장은 파일 flush 후 같은 디렉터리 안에서 rename한다.
Node가 지원하지 않는 디렉터리 fsync는 Windows에서 실행하지 않는다. Linux 경로의
디렉터리 fsync는 유지하며, Windows 정전 시 디렉터리 항목의 내구성을 검증했다고
주장하지 않는다. 이것은 SQLite 트랜잭션의 동기화 설정을 낮추는 변경이 아니다.
