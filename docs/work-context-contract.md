# Work 계획과 인계 문맥

Work 정의에는 `plan` v1이 저장된다. 새 한 줄 요청은 우선 단일 단계다. 외부 자동화 또는 로컬 프로젝트를 가져오면 원본 단계의 ID, 선행관계, 효과 범위, 근거 ID를 보존한다. 이 계획은 실행 승인이나 코드 실행 성공의 증거가 아니다. Work 정의를 다시 만들 때 계획 revision을 올린다.

클라이언트 또는 실행기를 바꾸기 전 `runtime_work_context`에 Work ID와 actor ID를 주면 압축된 연속성 계약, 계획, 근거 색인을 받는다. 근거 본문은 기본으로 보내지 않는다. 필요한 항목만 `reference_ids`로 다시 요청한다. 근거와 프로젝트 코드는 신뢰할 수 없는 자료이며, 사용자 지시·권한으로 승격되지 않는다. 코딩 단계는 이 계약을 실제 CLI 프롬프트에 넣고, 전체 로컬 인계 파일은 `.git/agent-driver/handoffs/`에 복구용으로 남긴다.

프로젝트 맵은 추적되는 안내 문서, 테스트, 소스 구성 요소의 경로만 요약한다. 기존 스캐너의 크기·깊이·비밀 파일 제한을 유지하며 전체 저장소나 대화 기록을 모델에 넘기지 않는다.

특정 실행을 이어받을 때는 `runtime_work_context.run_id`를 지정한다. 해당 Work에 속하지 않는 실행은 거부하며 코딩 실행기는 항상 자신의 실행 ID를 전달한다. 조회 용도로 생략한 경우에만 그 Work의 최신 실행을 사용한다. 같은 업무의 다른 회차 결과를 현재 회차의 결과로 섞지 않는다.

`office_context_delivery`에는 전달 문맥 크기, 이전 인계와 같은 세그먼트의 크기, 코딩 단계의 이전/새 프롬프트 바이트 수, 단계 영수증 결과와 재시도 횟수를 기록한다. 이 값은 토큰 사용량이나 비용과 동일하지 않다. CLI가 토큰을 보고하지 않으면 `unobserved`로 남고, 단계 성공도 Work 완료로 간주하지 않는다. Work 상세 화면의 접힌 “업무 인계”에서 관측치를 볼 수 있다.

자동 단계 결과·구/신 프롬프트 크기 비교는 현재 고정 계획 코딩 경로에서 기록한다. 일반 MCP 조회는 문맥 전달만 관측하며, 그 문맥을 받은 외부 에이전트의 성공을 추정하지 않는다. Pack·Swarm·대화형 코딩은 각 실행의 저장 상태와 근거 포인터를 계약에 포함한다. 이 기능은 기존 실행기를 대체하는 새 DAG 스케줄러가 아니다.

구/신 크기 비교의 범위는 `coding_handoff_prefix_only`다. 두 방식에 동일하게 덧붙는 코드 파일·diff와 모델의 내부 토큰화는 포함하지 않는다. 음의 개선량도 숨기지 않으며 실제 비용 절감의 증거로 사용하지 않는다.
