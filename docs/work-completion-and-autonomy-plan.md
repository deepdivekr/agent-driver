# Work 완료 경로 복구 및 자율 운영 계획 (초안)

Status: **Part A 진행 중.** 2026-10-01 사용자가 리팩토링 시작을 승인했다.
현재 작업 기준 문서이며, [커스텀 Pack 리팩토링 계획](custom-pack-refactoring-plan.md)은
배경으로 남는다. 충돌 시 3.4의 조항 표가 우선한다. 진행 기록:

Baseline: main f077e04 (PR #36 머지 포함). Branch: claude/workflow-validation-issues-u9mild.

## 1. 문제와 우선순위

**핵심 문제는 Work가 완료까지 도달하는 경로가 없다는 것이다.** 업무 자체는
실행되지만, 검증 게이트가 정상 결과를 거부하거나 실행기·supervisor가 완료 전에
`failed`·`awaiting_review`로 끝낸다. 간단한 업무도 완료 처리가 되지 않는 이유가 이것이다.

이 계획은 두 부분으로 나뉜다.

| 구분 | 내용 | 출처 | 순서 |
|---|---|---|---|
| **Part A. 완료 경로 복구** | 정상적으로 수행된 Work가 끝까지 완료 처리되게 한다 | 최초 진단 | **먼저, 단독으로 머지 가능** |
| Part B. 자율 운영 | 건별 승인 없이 위임 정책 안에서 스스로 진행하고, 성공을 Pack으로 재사용한다 | 사용자의 후속 요구 | Part A 이후 |

Part A는 Part B 없이도 그 자체로 가치가 있다. Part B의 자동 Pack화는 "성공" 판정이
믿을 만해야 의미가 있으므로 Part A가 전제다.

## 3. 원칙

### 3.1 절대 유지 (Part A·B 공통)
- 성공을 허위로 보고하지 않는다. **거짓 거부도 결함으로 측정한다.**
- 인증정보·개인 데이터를 노출하지 않는다.
- 사용자가 허용한 범위 밖의 행동을 하지 않는다. 모델이 스스로 권한을 만들지 못한다.
- 원래 요구와 이후 지시를 기준으로 삼는다. 기존 receipt는 지우거나 고쳐 쓰지
  않는다(“대체됨” 표시는 삭제가 아니다).

### 3.2 조건부 복구 (Part A에서 적용)
- 읽기: 언제든 다시 조회한다.
- 로컬 쓰기: Office 소유 산출물은 새 요청 ID로 다시 쓰거나, 같은 대상·같은
  내용이면 멱등 처리한다. 사용자 폴더 쓰기는 대상 상태를 다시 읽어 확인한 뒤 재시도한다.
- 외부 쓰기: 반영 여부를 먼저 조회해 확인한다. 반영됐으면 재사용하고,
  안 됐으면 재시도한다. 확인할 방법이 없을 때만 사람에게 알린다.

### 3.3 자율 운영 (Part B에서 적용)
- 위임 정책을 한 번 설정하면 건별 승인은 없다. 허용 범위 = 위임 정책이며 호스트가 집행한다.
- 성공 Work 자동 Pack화, 성적 기반 승격·강등.
- 계획 단계 Pack 자동 선택, 실패 시 같은 Work 안에서 새로 계획.
- 막히면 정책이 허용한 다음 수단으로 자동 전환.
- 정책으로도 대신할 수 없는 사람 개입은 세 가지뿐이다.

  | 경우 | 이유 | 빈도 |
  |---|---|---|
  | 사이트 최초 로그인·2단계 인증 | 신원 확인은 본인만 가능 | 사이트당 1회, 이후 전용 프로필에 유지 |
  | 필수 서비스의 CAPTCHA | 우회는 이용약관 위반·계정 차단 위험 | 대체 출처를 먼저 자동 시도 후에만 |
  | 정책 밖의 되돌릴 수 없는 외부 행동 | 결제·제3자 발송·제출 | 정책에서 유형별로 허용하면 0회 |

### 3.5 경량화 원칙 (Part A에서 적용)
- **검증은 위험도에 비례한다.** 위험도는 모델의 주장이 아니라 호스트가 기록한
  실제 실행 이력(닫힌 trace의 효과별 실행 수)으로 정한다. 되돌릴 수 있고 밖으로
  나가지 않는 결과일수록 가볍게, 외부에 영향을 준 결과일수록 엄격하게 검증한다.
- **금지는 지시문이 아니라 코드로 지킨다.** 호스트가 코드로 막는 행동은 모델
  지시문에서 뺀다. 모델이 그 행동을 시도하면 호스트가 교정 가능한 오류와 이유를
  돌려준다. 코드로 막지 못하는 것만 지시문에 남긴다.

## 4. Part A — 완료 경로 복구

각 단위는 독립적으로 머지할 수 있다. 단위마다 빌드, 관련 테스트, frozen quick
suite를 통과하고 진행 기록을 갱신한다. Part A는 사람 개입 방식(승인 절차)을
바꾸지 않는다.

### A0. 기준 문서 보정
- AGENTS.md와 기존 계획서 R3에 3.2 조건부 복구를 반영한다. 읽기·멱등 로컬 쓰기·
  반영 확인된 외부 쓰기는 재시도할 수 있다는 점을 명시한다.
- “거짓 거부도 결함”을 운영 불변조건에 추가한다.
- 완료 기준: 사용자 승인, Codex 등 다른 에이전트가 같은 문서를 읽음.

### A1. 검증 거짓 거부 제거
- 대체된 산출물: 같은 실행에서 같은 제목·형식의 Office 결과 파일을 나중에 다시 저장했으면
  호스트가 이전 파일과 그 readback에 `host_superseded_by`를 표시한다
  (`supersededOutputEvidence`). 표시된 기록의 `contradicts`/`unresolved_material`은
  배치 단계에서 즉시 거부하지 않고 최종 판단에 표시와 함께 넘긴다. 최종 판단은
  대체된 기록을 근거로 인용할 수 없다(`WORK_COMPLETION_SUPERSEDED_EVIDENCE_CITED`).
  모순 증거는 숨기지 않는다.
- 현재 기록의 모순은 계속 배치 단계에서 막는다. 구현 중 확인한 결과, 모든 모순을
  최종 모델 판단에 맡기면 현재 산출물의 실제 위반(행 누락·중복 키·잘못된 상태)도
  모델이 놓칠 수 있어 안전이 약해진다. 완화는 호스트가 코드로 증명할 수 있는
  대체된 산출물에만 적용하고, 나머지는 A2 수정 루프로 이유와 함께 넘긴다.
- 검사별 근거: 생성된 검사는 기존처럼 현재 receipt 전체를 받되(복합 검사 보호),
  대체된 산출물은 실행기가 직접 인용하지 않는 한 넓혀 붙이지 않는다. 원래 요청
  검사는 표시와 함께 전부 받는다(`src/work/supervisor.ts:40`).
- 표 데이터: 한 receipt의 셀 단위 인용 목록이 단일 기록 한도(40KB)를 넘을 때만
  행·열 색인(`<ref_prefix>.<row>.<col>`)으로 바꾼다. 모든 셀은 그대로 인용 가능하다.
  표가 아닌 receipt의 한도 초과는 계속 모델 호출 전에 거부한다
  (`src/work/completion.ts`의 배치 구성).
- 검증 호출 수: PR #36으로 크게 줄었지만 호출 하나하나가 실패 지점이다.
  Work당 검증 모델 호출 수를 기록한다.

### A2. 거부 뒤 수정 루프
- 거부 이유를 수정 입력에 넣는다(`completionRepairFeedbackSchema`).
- 수정 기회는 1회 고정이 아니라 예산 안에서 여러 번(기본 3회)으로 한다.
- 인용 오류·한도 초과 같은 검증기 기술 실패는 Work 보류가 아니라 검증 재시도로 처리한다.
- 검증기 오판 대응: 지금은 수정 단계에서 새 증거가 없으면 바로 보류된다
  (`src/work/client-executor.ts:398`). 실행기가 기존 증거로 충분하다고 판단하면,
  그 근거(어느 receipt의 어느 값인지)를 붙여 한 번 다시 검증받을 수 있게 한다.
  두 번째 판단은 다른 검증 모델이나 새 세션으로 하고, 결과와 상관없이 기록한다.
- 재개 시 수정 이력: 일반 재개로는 수정 이력(`completion_repair`)이 지워지지 않아
  재개 직후 다시 막힌다(`src/work/supervisor.ts:399-402`). 남은 예산으로 이어 간다.
- 로컬 쓰기 재시도: 3.2에 따라 허용한다(`src/work/client-executor.ts:490`).
- Swarm 경로에도 같은 수정 루프를 적용한다(`src/work/supervisor.ts:384`).

### A3. 실행기가 완료 전에 끝내는 지점 제거
- 완료 제안의 검사 누락·잘못된 ID는 출력 교정으로 처리하고 `failed`로 끝내지 않는다
  (`src/work/client-executor.ts:401`, `:519`).
- 결정 출력 오류 교정을 실행당 1회(`:370`)에서 예산 기반으로 바꾼다.
- 같은 잘못된 입력 반복(`:440`)은 `failed` 대신 그 도구를 이번 실행에서 제외하고
  다른 수단을 고르게 한다.
- 도구의 `failed` receipt(`:503`)는 Work 전체 실패가 아니라 그 도구의 실패로 기록하고,
  모델이 다른 수단을 고르게 한다. 효과가 불확실한 쓰기는 기존대로 reconciliation으로 간다.
- 저장 결과 재확인 예산 초과(`:422`)는 보류 대신 완료 제안 또는 수정 루프로 넘긴다.
- 실행 trace: receipt 재사용도 관측으로 기록한다(`:457`). 32개 관측 창과 별개로
  trace용 전체 이력을 보존한다(`:282`). PR #36 이후 봉인된 수집 업무는 trace가
  닫혀 있어야 통과하므로, 커스텀 Pack 회차에서 특히 먼저 고친다.

### A4. 진행 중인 Work가 멈추지 않게
- 시도 횟수: 실행이 새 관측이나 단계 진행을 만들면 시도 횟수를 줄이거나 초기화한다.
  진행 없는 반복만 시도로 센다(`src/work/supervisor.ts:245`, `:433`).
- 일시적 상태 자동 재개: `waiting_model`은 쿼터 회복 시각에, `retry_wait`은 백오프로
  자동 재개한다. `failed`는 진행 없는 반복이 예산을 넘었을 때만 남긴다
  (`src/work/supervisor.ts:241`).
- 설정 변경: 이 Work가 쓰는 설정(출처·대상·실행기·모델)이 바뀐 경우에만 멈춘다.
  설정 결속을 전체 해시에서 의존 대상 해시로 바꾼다
  (`src/interface/config.ts:145`, `src/work/supervisor.ts:216`, `:258`).
- 기존 상태 값은 호환 독자로 계속 읽는다.

### A5. 위험도에 비례한 검증
- 등급은 호스트가 닫은 실행 trace의 효과별 실행 수로 정한다
  (`createWorkRunTraceEvidence`, `src/work/supervisor.ts:329`). 모델 출력으로 바꿀 수 없다.
  trace가 닫히지 않았으면 외부 쓰기가 없었다고 증명할 수 없으므로 엄격 등급으로 본다
  (A3의 trace 수정이 선행되어야 하는 이유).

  | 등급 | 해당 Work | 검증 |
  |---|---|---|
  | 가벼움 | 읽기, 초안, Office 소유 산출물 쓰기만 있음 (조사·수집·변환·분류) | 코드 확인 + 짧은 의미 확인 1회 |
  | 중간 | 사용자 폴더·등록 대상의 로컬 쓰기 | 가벼움 + 대상 상태를 코드로 다시 읽어 변경 전후 비교 |
  | 엄격 | 외부 쓰기(발송·제출·게시 등) | 현재 경로 유지: 전체 receipt, 인용 검증, 닫힌 trace. A1·A2 개선 적용 |

- 가벼움 등급의 구성:
  - 코드 확인: 산출물을 실제로 다시 읽어 형식·해시·행 수를 확인하고, 봉인된 수집
    계약·native 검사가 있으면 그대로 쓴다. 출처 receipt가 실제로 있는지 확인한다.
  - 의미 확인: 검증 모델 호출 1회. 입력은 원래 요청, 최종 산출물 내용, 출처 요약
    (출처 ID·URL, 관측 시각, 행 수)이다. receipt별 배치 검사와 셀 단위 인용 목록은 쓰지 않는다.
    출력은 판정, 이유, 산출물에서 뽑은 인용 1–3개이고, 호스트가 인용이 산출물에 실제로
    있는지 확인한다.
  - 산출물이 한도를 넘으면 코드가 이미 확인한 부분(행 수·형식)은 빼고, 의미 확인에
    필요한 부분만 페이지로 나눠 준다.
- “제출·전송 없음” 같은 금지 행동 조건은 닫힌 trace의 실행 수로 코드가 판정하고
  모델에 묻지 않는다.
- 위치: 검증기 구성 `src/work/supervisor.ts:301`, 원래 요청 검사 경로 `src/work/completion.ts:529-`.
- 완료 기준:
  - 읽기 위주 조사·수집 Work는 코드 확인과 검증 모델 호출 1회(수정 시 +1)로 끝난다.
  - 외부 쓰기 Work는 엄격 경로를 타고 기존 테스트를 그대로 통과한다.
  - 등급이 trace에서만 정해짐을 테스트로 확인한다.

### A6. 금지는 지시문이 아니라 코드로
- 대상 지시문:
  - 실행: `src/work/client-executor.ts:122` (완료·단계 지시 포함, 매 턴 7.5KB)
  - 검증: `src/work/completion.ts:33-36`, 배치 지시 `:189-` (기본 7.2KB)
  - 정의·재계획: `src/work/runtime.ts:23`, `:38` (6.3KB, 14.1KB)
- 방법:
  1. 지시문의 금지 문장을 목록으로 만들고, 각각 그 행동을 막는 호스트 코드를 찾는다.
  2. 코드로 막고 있으면 지시문에서 뺀다. 대신 “모델이 그 행동을 시도하면 호스트가
     거부하고 교정 가능한 이유를 돌려준다”는 테스트를 문장마다 하나씩 둔다.
  3. 필요한 금지인데 코드로 막지 않는 것은 먼저 코드로 막은 뒤 뺀다.
  4. 코드로 확인할 수 없는 의미 규칙(원래 요청을 좁히지 말 것, 출력 형식 해석 등)만 남긴다.
  5. 거부 메시지는 모델이 바로 고칠 수 있게 짧고 구체적으로 쓴다
     (기존 `WorkClientToolInputError` 경로 재사용).
- 이미 코드로 막고 있어 뺄 수 있는 예: 목록에 없는 도구 호출, 없는 evidence ID 인용,
  같은 잘못된 입력 반복, 범위·승인 우회, 인용문 위조, 닫히지 않은 trace 인용.
- 목표: 실행·검증·재계획 지시문을 각각 절반 이하로 줄인다
  (7.5KB → 3.5KB 이하, 7.2KB → 3.5KB 이하, 14.1KB → 7KB 이하).
  크기를 테스트로 기록해 다시 커지지 않게 한다.
- 완료 기준: 뺀 문장마다 대응하는 거부 테스트가 있고, A7 실제 모델 측정에서
  완료율이 떨어지지 않는다.

### B3. 계획 단계 Pack 자동 선택

- 완료 기준: 비슷한 두 번째 Work가 Pack을 재사용하고, 첫 실행 대비 모델 호출이 줄어든다.

- 봉인된 수집 계약(`src/work/execution-tools.ts:438`): 사용자가 출처를 지정하지
  않았다면 출처가 막혔을 때 에이전트가 새 계약을 다시 봉인할 수 있다.
  원래 요청 검증이 바뀐 출처를 그대로 확인한다.
- 완료 기준: 백그라운드 차단·로그인 만료·출처 장애를 넣은 시험에서 사람 개입 없이
  다음 수단으로 넘어가 완료한다(최초 로그인 제외).

### B6. 실행 중 방향 전환
- Swarm: 단계가 바뀌면 정지하는 대신(`src/work/swarm-executor.ts:200-202`)
  결속이 같은 작업자는 유지하고, 바뀐 단계만 다시 계획해 이어 간다.
- 실행 방식 변경(`src/work/supervisor.ts:386`): 기존 receipt를 상속 증거로 넘겨 이어 간다.
- 완료 기준: 실행 중 지시 변경이 정지 없이 반영되고, 끝난 단계는 다시 실행하지 않는다.

### B7. 흩어진 봇 통합 (이후)
가져온 Hermes·원격 OpenClaw 등은 지금 “원본에 메시지 보내기” 수준으로 제어된다.
B1–B6 이후, 가져온 봇의 단계 관측과 방향 전환을 같은 Work 모델로 끌어온다.

### Part B 지표 (A7 측정에 추가)
- Work당 사람 개입 횟수(목표: 새 사이트 로그인 외 0회)
- Pack 재사용 적중률, 반복 회차의 모델 호출·시간 감소율
  (목표: 정식 Pack 회차의 모델 호출이 첫 실행 대비 50% 이하)

## 6. 순서

| 차수 | 단위 | 결과 |
|---|---|---|
| **1차** | A0 → A1, A2, A3(병행) → A4 → A5, A6(병행) → A7 | **간단한 업무가 완료까지 도달하고, 검증·지시문이 가벼워짐** |
| 2차 | B0 → B1 → B2 → B3 → B4 | 사람 승인 없이 진행, 성공이 Pack이 되고 재사용되고 빨라짐 |
| 3차 | B5, B6 | 막혀도 스스로 넘어가고, 방향 전환에도 멈추지 않음 |
| 이후 | B7 | 외부 봇 통합 관제 |

A5는 A3의 trace 수정 이후에 착수한다(등급 판정이 닫힌 trace에 의존).
A7 측정은 1차의 각 단위마다 수행하고, 2차·3차에도 계속한다.

## 7. 위험과 대응

| 위험 | 대응 |
|---|---|
| 검증 완화로 거짓 성공 증가 | 거짓 성공률을 함께 측정, 기존 방지 테스트 유지, 모순 증거는 숨기지 않고 최종 판단에 넘김 |
| 가벼운 검증 등급에서 거짓 성공 | 등급은 닫힌 trace로만 결정, 외부 쓰기는 항상 엄격 등급, 거짓 성공률 표본 측정 |
| 지시문에서 뺀 금지가 실제로는 집행되지 않음 | 뺀 문장마다 코드 거부 테스트 필수, 테스트 없는 문장은 빼지 않음 |
| 재시도 확대로 중복 효과 | 3.2 조건부 복구만 허용, 효과 불확실 쓰기는 기존 reconciliation 유지 |
| 진행 기반 시도 계산으로 무한 실행 | Work당 시간·모델 호출 예산 상한 |
| 잘못된 절차가 Pack으로 퍼짐 (Part B) | 후보 → K회 검증 후 승격, 연속 실패 시 강등, 매 회차 원래 요청 검증 유지 |
| 정책이 너무 넓음 (Part B) | 결제·제3자 발송·제출은 기본 거부, 행동마다 정책 버전 기록 |
| 사용자 화면 충돌 (Part B) | 기본은 전용 VM, 사용자 데스크톱은 자리 비움에만·기본 꺼짐 |
| 여러 에이전트 동시 작업 충돌 | 단위별 파일 소유권 지정, 같은 main 기준에서 작업 |
